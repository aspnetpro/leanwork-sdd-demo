## Findings detalhados

### 🟡 Importantes

#### R-01 — `Pages/Privacy.cshtml` sem RN/CA, fora do escopo "uma única tela"

- **Eixo:** 3. Aderência ao spec (PRD + Arquitetura)
- **Referência cruzada:** PRD §1 ("Uma aplicação web com **uma única tela**"), arquitetura §3.1 (meta concreta: "o código de produção cabe em até 10 arquivos")
- **Evidência:** `src/Encurtador.Web/Pages/Privacy.cshtml`, `Pages/Privacy.cshtml.cs`, referenciado em `Pages/Shared/_Layout.cshtml:27` e `:42`
- **Descrição:** O template padrão do Razor Pages criou uma segunda tela (`Privacy`) com link no menu e no rodapé do layout. O PRD é explícito: o sistema tem uma única tela, sem painel, sem página adicional. `Privacy.cshtml` não implementa nenhuma RN, não é validada por nenhuma CA, e consome 2 dos ~10 arquivos de produção que a arquitetura orça para o atributo "Legibilidade" — orçamento que ainda vai receber `Dados/`, `Servicos/` e as migrations das Fases 2 e 3.
- **Por quê é Importante:** não quebra nada hoje, mas se ninguém remover, o sistema chega à Fase 5 acima do teto declarado na própria arquitetura, e a "matriz de rastreabilidade" do README (T-12) vai ter um arquivo de produção sem nenhuma linha correspondente — o oposto do que a palestra defende.
- **Sugestão de correção:** remover `Pages/Privacy.cshtml(.cs)` e o link correspondente em `_Layout.cshtml` agora (é trivial, e T-09/T-10 vão reescrever o layout de qualquer forma), ou abrir explicitamente essa remoção como parte do escopo declarado de T-10 no plano.

#### R-02 — T-01 marcada como concluída sem commit correspondente

- **Eixo:** 1. Aderência ao plano / 2. Rastreabilidade
- **Referência cruzada:** Plano §2 ("um commit por tarefa. [...] o que permite mostrar em palco a evolução do repositório amarrada às tarefas do plano"), §11 (Histórico de execução)
- **Evidência:** `git log -1` mostra apenas o commit anterior à criação deste projeto; `git status` lista todo `demos/encurtador-url/` como não rastreado. A linha de T-01 na tabela "Histórico de execução" do plano tem `Commit: —`.
- **Descrição:** O checklist de "pronto" da tarefa (build, test, run) está satisfeito, mas a estratégia de entrega do plano depende de um commit por tarefa para que a cadeia `ADR → RN → CA → T → commit` seja auditável no repositório — que é o próprio argumento da palestra. Sem commit, a tabela de histórico fica com uma lacuna que vai se acumular a cada tarefa seguinte se não for corrigida agora.
- **Por quê é Importante:** não impede T-02 de começar, mas adiar o commit indefinidamente é como a dívida se acumula silenciosamente — e é exatamente o tipo de coisa que o pipeline SDD existe para evitar.
- **Sugestão de correção:** commitar o estado atual de T-01 (idealmente já incorporando a correção de R-01) com mensagem citando `T-01`, antes de iniciar T-02.

### 🟢 Sugestões

#### R-03 — Middleware de HTTPS e autorização sem uso real no pipeline

- **Eixo:** 5. Qualidade do código
- **Referência cruzada:** PRD §4.2 ("Deploy em cloud, domínio próprio e HTTPS com certificado real" fora de escopo), PRD §10 ("Não há controle de acesso")
- **Evidência:** `src/Encurtador.Web/Program.cs:16` (`app.UseHttpsRedirection();`) e `:20` (`app.UseAuthorization();`)
- **Descrição:** O template padrão inclui redirecionamento HTTPS e middleware de autorização, mas o PRD descarta HTTPS real e qualquer controle de acesso. O efeito já é observável: o smoke test desta review (`dotnet run` + `curl`) registrou `warn: Failed to determine the https port for redirect.` no log de inicialização — ruído que pode confundir durante a demo em palco, onde o log limpo importa (arquitetura, riscos: "cache de navegador falsear o comportamento durante a demonstração").
- **Sugestão de correção:** remover as duas linhas agora, já que nenhuma tarefa do plano depende delas, ou registrar explicitamente como decisão consciente se houver razão para mantê-las (ex.: preparar terreno para um cenário de deploy real futuro — o que contradiria os não-objetivos declarados).

## Verificação da Decisão Arquitetural

### ADR-001 — Aplicação única em Razor Pages, com o redirect fora do roteamento de páginas

- **Decisão original:** um único projeto web ASP.NET Core, sem separação em API + frontend, sem projetos de camada.
- **Implementação:** `src/Encurtador.Web/Encurtador.Web.csproj` usa `Microsoft.NET.Sdk.Web`, é o único projeto deployável da solution. O endpoint de redirect (T-08) ainda não existe — correto, fora do escopo de T-01.
- **Conformidade:** ✅ Um projeto web, sem indireção adicional.

### ADR-008 — Suíte xUnit com testes nomeados pelo ID do critério de aceite

- **Decisão original:** xUnit em projeto separado, referenciando o projeto web, com `Microsoft.AspNetCore.Mvc.Testing` disponível desde o início para os testes de rota das tarefas seguintes.
- **Implementação:** `tests/Encurtador.Tests/Encurtador.Tests.csproj` referencia `src/Encurtador.Web/Encurtador.Web.csproj` (`ProjectReference`) e já inclui `Microsoft.AspNetCore.Mvc.Testing` 10.0.11 — exatamente o que o plano pediu para evitar uma interrupção em T-08.
- **Conformidade:** ✅ Projeto de teste separado, dependência de integração já presente.

### 🟢 Sugestões

Melhorias opcionais, ficam a critério do autor.

#### R-01 — CA-09 não verifica persistência por contagem, só pelo retorno do serviço

- **Eixo:** 4. Cobertura de teste
- **Referência cruzada:** CA-09, RN-07
- **Evidência:** `tests/Encurtador.Tests/ServicoDeEncurtamentoTests.cs:38-49` (`CA_09_ColisaoDeCodigo_ResolvidaPorNovoSorteio`)
- **Descrição:** O teste assere `resultado.Sucesso` e `resultado.Codigo == "nV7zQ1m"`, o que já é evidência forte (o caminho de sucesso só é alcançado após `SaveChangesAsync` concluir sem exceção). Mas, diferente de CA-10 — que assere explicitamente `dbContext.Links.CountAsync() == 1` para provar "nada foi gravado" — CA-09 não faz o contraponto de contar `2` registros para provar "a gravação foi concluída".
- **Por que não é Bloqueante/Importante:** o resultado `Concluido` só é retornado depois de `await dbContext.SaveChangesAsync()` ter sucesso, então a garantia já existe por construção do código, não é uma lacuna real de cobertura.
- **Sugestão de correção:** adicionar `Assert.Equal(2, await dbContext.Links.CountAsync())` ao final do teste, espelhando o rigor já aplicado em CA-10.

#### R-02 — Nome do método assíncrono sem sufixo `Async`

- **Eixo:** 5. Qualidade do código
- **Evidência:** `src/Encurtador.Web/Servicos/ServicoDeEncurtamento.cs:11` (`public async Task<ResultadoEncurtamento> Encurtar(...)`)
- **Descrição:** O método é assíncrono mas não segue o sufixo `Async`, comum em convenções .NET. O projeto ainda não tem outro método assíncrono customizado para comparar (os únicos `async` existentes até T-06 são chamadas diretas do EF Core), então não há convenção estabelecida sendo quebrada — mas vale fixar o padrão agora, antes que T-08/T-09 criem mais métodos assíncronos com nomes divergentes.
- **Sugestão de correção:** decidir e documentar (ex. no `CLAUDE.md`) se o projeto adota o sufixo `Async` para métodos de serviço assíncronos, e aplicar retroativamente se sim.

## Cobertura por RN (Implementa)

### RN-07 — Unicidade do código garantida pelo banco, retry até 5 tentativas, falha genérica sem gravar

- **Como foi implementada:** `ServicoDeEncurtamento.Encurtar` sorteia código, adiciona a entidade e chama `SaveChangesAsync` dentro de um `for` de até 5 iterações. Em `DbUpdateException` cujo `InnerException` é `SqliteException` com `SqliteExtendedErrorCode == 2067` (`SQLITE_CONSTRAINT_UNIQUE`), destaca a entidade do change tracker e tenta de novo. Esgotadas as tentativas, devolve `ResultadoEncurtamento.Falha("Não foi possível gerar o link agora. Tente novamente.")` — mensagem idêntica à tabela do PRD §8.
- **Evidência:** `src/Encurtador.Web/Servicos/ServicoDeEncurtamento.cs:13-38`
- **Status:** ✅ Implementada corretamente. O filtro por `SqliteExtendedErrorCode` (não apenas `SqliteErrorCode` genérico) evita o risco explícito no plano de "engolir qualquer `DbUpdateException` como colisão".

### RN-08 — Mesma URL encurtada mais de uma vez produz códigos distintos, sem deduplicação

- **Como foi implementada:** Cada chamada a `Encurtar` cria uma nova entidade `Link` e persiste um registro novo — não há consulta prévia por URL existente.
- **Evidência:** `src/Encurtador.Web/Servicos/ServicoDeEncurtamento.cs:15-20`
- **Status:** ✅ Implementada corretamente.

### RN-09 — Cada link persiste código, URL de destino exata e data/hora de criação em UTC

- **Como foi implementada:** `Link` é construído com `Codigo = geradorDeCodigo.Gerar()`, `UrlDestino = urlValidada` (recebida sem transformação) e `CriadoEm = DateTime.UtcNow`.
- **Evidência:** `src/Encurtador.Web/Servicos/ServicoDeEncurtamento.cs:16-20`
- **Status:** ✅ Implementada corretamente.

## Cobertura por CA (Valida)

### CA-08 — Mesma URL encurtada duas vezes gera códigos distintos

- **Teste correspondente:** `tests/Encurtador.Tests/ServicoDeEncurtamentoTests.cs::CA_08_MesmaUrlEncurtadaDuasVezes_GeraCodigosDistintos`
- **Cobre o cenário Gherkin completo?** Sim — encurta a mesma URL duas vezes via o serviço registrado em DI (gerador real `GeradorDeCodigoBase62`), assere códigos distintos e que ambos os registros apontam para o mesmo `UrlDestino`. ### CA-09 — Colisão de código é resolvida por novo sorteio

- **Teste correspondente:** `tests/Encurtador.Tests/ServicoDeEncurtamentoTests.cs::CA_09_ColisaoDeCodigo_ResolvidaPorNovoSorteio`

- **Status:** ✅ (ver R-01 para sugestão de reforço)

### CA-10 — Falha após esgotar as tentativas de geração

- **Status:** ✅

## Verificação da Decisão Arquitetural

### ADR-002 — SQLite via EF Core, com índice único no código curto

- **Decisão original:** O índice único no banco garante a unicidade que o gerador tenta em memória; a aplicação reage ao conflito em vez de consultar antes de inserir.
- **Implementação:** `ServicoDeEncurtamento` não faz nenhuma consulta de existência prévia — insere direto e reage a `DbUpdateException`/`SqliteException` de violação de unicidade.
- **Conformidade:** ✅

### ADR-003 — Código curto de 7 caracteres Base62, gerado aleatoriamente com retry em colisão

- **Decisão original:** Como o código é sorteado (não sequencial), a unicidade não é garantida na geração — é garantida pelo banco, com retry na aplicação.
- **Implementação:** Laço de até `MaximoDeTentativas = 5`, novo sorteio via `IGeradorDeCodigo.Gerar()` a cada tentativa, change tracker limpo entre tentativas (`EntityState.Detached`) para não arrastar a entrada falha para a próxima gravação.
- **Conformidade:** ✅

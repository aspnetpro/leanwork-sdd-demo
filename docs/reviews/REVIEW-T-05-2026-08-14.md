## Findings detalhados

### 🟢 Sugestões

Melhorias opcionais, ficam a critério do autor.

#### R-01 — `NormalizarHost` não trata hosts IPv6 entre colchetes

- **Eixo:** 5. Qualidade do código
- **Referência cruzada:** RN-03
- **Evidência:** `src/Encurtador.Web/Servicos/ValidadorDeUrl.cs` (método `NormalizarHost`, corte em `host.IndexOf(':')`)
- **Descrição:** Um host IPv6 literal como `[::1]:8080` tem `:` como parte do próprio endereço, não só como separador de porta — `IndexOf(':')` cortaria no primeiro `:` do endereço, não na porta. Nenhum CA ou RN do PRD menciona IPv6, e o cenário de demo (`localhost` / `curto.local`) não exercita esse caminho, então não é um gap de escopo. Fica registrado como limitação conhecida caso o host da requisição algum dia venha de um ambiente com IPv6 literal.
- **Sugestão de correção:** Nenhuma ação necessária para a demo. Se o escopo mudar, tratar hosts entre colchetes antes do corte por `:`.

#### R-02 — Commit ainda não criado para T-05

- **Eixo:** 2. Rastreabilidade
- **Referência cruzada:** —
- **Evidência:** `git status` mostra os arquivos da tarefa como modificados e não commitados.
- **Descrição:** A convenção do plano (§2) é um commit por tarefa, com o ID `T-XX` na mensagem, e a tabela de histórico (§11) referencia o hash do commit. Isso ainda não aconteceu para T-05 — mesmo padrão observado em T-04 (R-02 daquele review).
- **Sugestão de correção:** Commitar com mensagem referenciando `T-05` e preencher o hash na tabela de histórico de execução do plano.

## Cobertura por RN (Implementa)

### RN-03 — Destino no próprio host é rejeitado

- **Como foi implementada:** Após as três primeiras checagens, `NormalizarHost(uri.Host) == NormalizarHost(hostDaRequisicao)` compara o host da URL de destino (já normalizado pelo próprio parser `Uri`) com o host recebido como parâmetro, ambos passados por `NormalizarHost` (lowercase + corte antes do primeiro `:`). O host da requisição entra como parâmetro do método — o validador continua sem depender de `HttpContext`, como o plano exigia para manter CA-05 testável sem subir a aplicação.
- **Evidência:** `src/Encurtador.Web/Servicos/ValidadorDeUrl.cs` (novo parâmetro `hostDaRequisicao` na assinatura de `Validar`, checagem antes do `return Aceita`, e método privado `NormalizarHost`)
- **Status:** ✅ Implementada corretamente — `CA_05_DestinoNoProprioHost_DeveSerRejeitado`, `CA_05_DestinoNoProprioHostComCaixaDiferente_DeveSerRejeitado` e `CA_05_DestinoNoProprioHostComPortaDiferente_DeveSerRejeitado` verdes, cobrindo o caso base e os dois riscos anotados na tarefa (case-insensitividade de DNS e porta desconsiderada).

### RN-05 — Ordem das validações com short-circuit

- **Como foi implementada:** A ordem no código é obrigatoriedade/trim (RN-04) → esquema (RN-01) → tamanho (RN-02) → host (RN-03), cada `if` com `return` imediato — não houve reordenação das três checagens já existentes de T-04, só o acréscimo da quarta ao final, preservando a sequência que o plano fixa.
- **Evidência:** `src/Encurtador.Web/Servicos/ValidadorDeUrl.cs` (sequência dos quatro `if` dentro de `Validar`)
- **Status:** ✅ Implementada corretamente — `CA_17_EntradaComMultiplasViolacoes_ExibeApenasAPrimeira` prova que uma entrada com esquema `javascript:` e 3000 caracteres (violando RN-01 e RN-02 simultaneamente) devolve só a mensagem de esquema, nunca a de tamanho — a checagem de esquema vem antes e interrompe o processo.
